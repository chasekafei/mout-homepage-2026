# MouT.me 个人网站设计与实施方案

> 状态：设计与交互基线，尚未进入正式开发
> 更新日期：2026-09-05
> 品牌：MouT.me

## 0. 文档用途

这份文档记录 MouT.me 个人网站目前已经确认的设计判断、内容聚类、交互规则和实施顺序，供后续设计、开发、复盘和取舍使用。

它不是最终视觉稿，也不是完整 PRD。视觉概念图仍然允许迭代，但已经确认的核心体验规则不应在实现过程中被普通网页模板、默认组件或无意义的 3D 特效替代。

## 1. 产品目标

### 1.1 对外目标

网站的第一任务不是证明项目商业上成功，也不是让访客像面试官一样审查履历，而是让访客在自然浏览中形成一个清晰的人物印象：

- 对新事物有强烈好奇心；
- 喜欢突破边界，不为职业和技术栈设限；
- 擅长把看似不相关的东西联系起来并亲手做出来；
- 情绪稳定、思路清醒、对体验和细节较真；
- 对人的处境、关系和表达方式保持共情；
- 有真实的生活、玩心和长期兴趣，不只是一个职业履历。

第一优先访客是互联网同行、招聘者，以及因为某个产品或观点而想进一步认识 MouT.me 的人。网站需要让这些人快速看懂你在做什么，但不应让他们感觉自己正在参加一场项目答辩。

### 1.2 对内目标

网站还要成为一个低摩擦的个人输出系统，让以下内容可以持续增加：

- 文章、Newsletter 和短想法；
- 独立产品和实验；
- 音频、播客和可试玩项目；
- 游戏、电影、旅行、乒乓球和猫；
- 仍在形成中的判断，而不是只有完成后的成果。

## 2. 人物定位

### 2.1 核心人格

四个核心词：**好奇、突破、不设限、共情**。

它们不是四个并列标签，而是一条行为链：

> 好奇让 MouT.me 注意到新的可能；突破让他不满足于已有答案；不设限让他愿意跨过岗位和能力边界亲手实现；共情决定这些探索最终应该为谁服务。

补充人格：清醒、情绪稳定、创意来自联想、持续高强度、身先士卒、略带自嘲。

一个可用于内部校准的描述：

> 表面情绪稳定，脑子里一直在施工。

一个可作为首页文案候选的描述：

> 我喜欢把看起来不相关的东西连在一起，然后把它做出来。

### 2.2 设计上的反差

网站需要同时表现两种状态：

- 外部：稳定、清晰、克制、容易进入；
- 内部：高强度、好奇、持续变化、藏有大量实验。

因此不能使用满屏动效、噪音化粒子或持续炫技来代表“突破”。突破应该体现在场景切换、物件行为和内容关联上；共情应该体现在可读性、反馈和不增加访客负担上。

## 3. 核心体验概念

### 3.1 一句话

> **同一个 MouT 角色，坐在不同状态里；场景变化，物件打开经历。**

这不是开放世界，也不是自由驾驶游戏。访客不需要主动在空间里行走或寻找项目。每次只呈现一个完整场景，导航负责切换状态，场景里的少量物件负责打开内容。

### 3.2 固定元素

以下元素在所有状态中保持不变：

- 角色的视觉形象：黑色几何头发、眼镜轮廓、黑色上衣、像素化比例；
- 角色胸前的小标记：**永结童心**；
- 角色在画面中的锚点位置和坐姿；
- 主摄像机的构图和观察角度；
- MouT.me 的品牌标记；
- 返回、状态切换和内容打开的基本交互规则。

角色可以被制作成一个固定的 2.5D/低面数资产，不依赖精细面部。照片只作为黑发、眼镜、黑色上衣和整体气质参考，像素头像是主要视觉参考。

### 3.3 视觉概念

整体方向是**明亮的、平面化的 2.5D/3D 舞台设计**：

- 固定镜头和明确构图；
- 大块几何体、清晰硬阴影、少量材质细节；
- 体素、纸张、屏幕、塑料、布料和手绘线稿可以共存；
- 不追求写实，也不做可爱的玩具世界；
- 不使用统一的黄色背景；黄色是 MouT.me 的识别色之一，不是每个场景的底色；
- 不使用紫色 AI 官网、赛博朋克、霓虹网格、默认粒子背景或玻璃卡片。

### 3.4 暂定颜色系统

色值是设计阶段的暂定值，正式实现前需要从被确认的视觉稿重新采样。

| 角色 | 暂定方向 |
|---|---|
| 品牌识别 | 头像黄 `#FFE500`、深黑 `#111111`、少量红色 `#F03838` |
| 创作 | 纸白、墨黑、薄荷绿、暖橙 |
| 游戏 | 像素青、石墨黑、珊瑚红、少量品牌黄 |
| 工作 | 冷淡蓝灰、石墨黑、青绿色、红色 active state |
| 出发 | 天空蓝、山地绿、道路灰、砖红或沙色 |

每个场景拥有自己的主环境色和材质，但角色的黑色服装、胸前标记和品牌点色持续提供连续性。

## 4. 场景与内容架构

### 4.1 状态总览

导航状态暂定为：

`此刻 / 创作 / 游戏 / 工作 / 出发 / 和我聊聊`

`和我聊聊` 可以是独立状态，也可以在每个场景中作为角色附近的动作入口。它不应强迫访客先进入聊天才能理解网站。

### 4.2 此刻

定位：当前生活和当前创作的入口，不是完整 About 页。

可能呈现：

- 角色坐在最中性的环境里；
- 一个当前正在做的独立项目；
- 最近的一条想法或正在研究的问题；
- AI 分身入口；
- 两只猫作为生活状态的存在。

此刻场景可以是最简洁的状态，避免一开始就承载完整履历。

### 4.3 创作

定位：内容、播客和独立产品的创作状态。

核心物件：

1. **通用报纸 / 期刊**
   - 不写“社思现场”，因为未来会放更多文章、观察、Newsletter 和其他内容。
   - 代表持续发布和整理内容的行为，而不是某一个固定栏目。
   - 点击后进入文章、Newsletter 和短想法索引。

2. **麦克风与波形**
   - 暂时只代表 CrossPod 和播客内容。
   - 不把 TIYA、AI VTuber 等工作经历混入这里。
   - 鼠标移入时波形响应，点击后可以试听和浏览节目。

3. **独立产品原型仓 / 产品发射台**
   - 不使用普通文件夹语义。
   - 使用一个带有插槽、可拔插原型模块和空置扩展位的实体装置。
   - 代表 Find Muse、Dimensional Inn、stpHQ 以及未来的个人产品集合。
   - 每个模块可以独立展开，但 3D 容器本身不随项目数量增长而重新设计。

4. **三阶魔方**
   - 明确使用 3×3×3 魔方，不使用抽象立方体。
   - 默认持续自动旋转，鼠标靠近时改变旋转速度或停顿。
   - 点击后进入旧个人网站和早期 Web 实验。

5. **两只猫**
   - 烧酒：狸花猫；
   - 小八：英短蓝白。
   - 猫是生活层，不承担项目分类。
   - 可以有轻微的抬头、眨眼、尾巴动作；点击后打开猫的照片或简短记录。

### 4.4 游戏

定位：老玩家、游戏创作者和玩心，不承担 AI 工作经历。

核心物件：

1. **GBA**
   - 代表婚礼邀请函小游戏。
   - 点击后直接进入可试玩版本，或先出现简短说明。

2. **童年游戏机 / 电视**
   - 代表 FC、MD、小学时期同学围着电视一起玩的记忆。
   - 重点是共同玩耍和早期游戏经验，不只是展示硬件。

3. **游戏收藏 / 存档入口**
   - 代表长期游玩、Steam 游戏收藏和对游戏机制的理解。
   - 不需要真的堆一千个游戏盒子，可使用持续延伸的存档、卡带或收藏架结构。

4. **预留扩展位**
   - AI 围棋、UNO、掼蛋、海龟汤和 LOL 陪玩暂时不放入这个场景。
   - 未来如果出现更适合“个人玩心”而不是“工作经历”的内容，再使用此入口。

### 4.5 工作

定位：产品能力的行业来源，但当前焦点是 AI / AI Agent。

#### 主焦点：空间智能助手

借鉴免手操作、语音唤醒、环形投影、上下文理解和工具调用的交互方式，不使用任何钢铁侠、贾维斯、盔甲、头盔或现有 IP 形象。

中央物件是一个非人形的 AI Agent 核心：

- 黑色和米白色几何核心；
- 一圈青色或薄荷色指令环；
- 环内有随语音响应的波形；
- 搜索、文档、图片、邮件、数据库和日程等工具以实体模块围绕核心出现；
- 红色连接点表示当前调用的工具。

它应该像一个正在聆听、理解和协作的空间助手，而不是服务器、显示器或普通后台。

#### 次级行业入口

其他经验作为 AI 能力的来源，退到核心周围：

- **社交**：TIYA、语音房、熟人社交、AI VTuber；视觉可用圆形语音房和连接节点。
- **游戏**：游戏创业、商业小游戏、自研游戏；视觉可用关卡格和控制器。
- **品牌营销 / 游戏化互动**：微信 Campaign、Fendi、迪士尼、中国长城；视觉可用活动分镜、跑酷路径和品牌色块。
- **电子政务**：海珠政务、政务微信和小程序；作为最早的经历放在远处、低亮度的档案模块中。

不把五个行业做成五张平等卡片。AI / Agent 必须是角色正前方最大的视觉焦点，其他行业只作为它背后的能力来源。

### 4.6 出发

定位：远程工作后的移动生活、旅行、电影和乒乓球。

固定部分：

- 角色、车内座位、仪表盘、方向盘和摄像机固定；
- 角色姿态在所有目的地状态中保持一致。

可变部分：

- 车窗外一次只显示一个目的地；
- 车内路书或目的地旋钮负责切换地点；
- 切换时只更换窗外场景、天气、光线和少量地点物件。

地点视觉应使用真实的个人经历和标志性地点：

- 新疆：赛里木湖、喀纳斯、北疆公路；
- 格鲁吉亚：巴统海边与“阿里与尼诺”雕像；
- 日本：福冈、北海道、名古屋等不同城市或地区；
- 卡塔尔：多哈；
- 香港、澳门、成都、重庆、大连、长沙等可归入短途/城市记录。

地点不应做成旅游网站的地标拼贴。每个目的地最好由“一个主要景观 + 一种光线/色调 + 一件个人物件”组成。比如巴统使用海边、阿里与尼诺和一张旅行票据；新疆使用开阔公路、湖泊或山地和车内路书。

固定物件：

- 电影票或放映片段：进入电影记录；
- 乒乓球拍或比赛标记：进入比赛旅行和观看记录；
- 行李或车内小物件：进入远程工作与出发记录。

## 5. 物件打开后的呈现方式

### 5.1 三级交互协议

每个物件统一采用三级反馈：

1. **移入**：物件有轻微、可理解的响应，并出现不超过两行的短说明。
2. **点击**：物件在原位置展开一个内容预览，场景降低亮度或饱和度，但不完全消失。
3. **继续操作**：进入完整阅读、音频、试玩项目或独立内容 URL。

每个物件都必须能回答两个问题：它对应哪段真实经历，点击后能获得什么内容。如果不能回答，就删除它。

### 5.2 内容类型映射

| 内容类型 | 推荐呈现 |
|---|---|
| 短想法 | 场景内展开一张简短内容平面，支持继续阅读 |
| 长文章 / Newsletter | 使用实际 HTML 阅读层，保留报纸或纸张视觉来源，不把正文烘焙进图片 |
| 播客 / 音频 | 波形展开成播放轨道，支持播放、暂停和进度 |
| 独立产品 | 原型模块拔出，展示一句介绍、状态、入口和少量图片 |
| 可试玩项目 | 在当前空间内打开游戏层，或进入独立试玩页 |
| 工作经历 | 从行业入口进入项目集合，不默认显示数据答辩式案例 |
| 旅行 | 车窗保持场景，外部景色或目的地内容层变化 |
| AI 分身 | 角色附近出现字幕、语音波形或小型屏幕，不跳到普通客服窗口 |
| 猫 | 轻量照片/记录层，作为生活内容，不改变网站主结构 |

### 5.3 内容层的视觉规则

- 不使用默认居中的 Modal；
- 内容从被点击的物件位置展开，像物件打开了内部空间；
- 长文本必须使用 HTML/CSS，以保证复制、搜索、键盘访问和移动端阅读；
- 关闭或返回动作明确且始终可用，`Esc` 返回场景；
- 内容层不能遮住主要导航，也不能阻断浏览者回到其他状态；
- 预览层可以有场景质感，但不能牺牲正文可读性。

## 6. 场景切换

### 6.1 不变量与变量

切换时保持：

- 角色模型、位置、比例、坐姿；
- 摄像机和主要构图；
- MouT.me 标记和“永结童心”标记；
- 场景切换控件和返回逻辑。

切换时变化：

- 背景环境；
- 主色与材质；
- 场景道具；
- 环境音；
- 交互热点；
- 少量灯光和阴影。

### 6.2 统一转场节奏

每次转场使用约 `0.8–1.2 秒` 的时间线：

1. **响应**：当前状态的导航或核心物件先回应点击。
2. **收拢**：当前场景物件向共享地面、阴影或中心结构收拢。
3. **换景**：背景材质、灯光和环境物件替换或变形。
4. **稳定**：新场景停下，交互热点逐个恢复。

不使用大幅摄像机飞行、不让用户在场景中移动，也不使用随机粒子爆炸作为通用转场。

### 6.3 有个人含义的变形

转场应该尽量由真实物件之间的关系产生：

- 创作 → 工作：报纸边缘折叠成原型装置，麦克风波形变成 AI 指令环。
- 工作 → 游戏：AI 工具模块收缩成像素块，屏幕外框变成电视或 GBA。
- 游戏 → 出发：电视画面拉伸成车窗，像素路径变成公路。
- 出发 → 创作：车窗外的道路或路线回卷成报纸边缘或音频波形。
- 任意状态 → 和我聊聊：环境停留在原地，其他物件安静下来，角色附近出现对话层。

### 6.4 交互状态管理

使用明确的状态机，不依靠多个组件各自猜测当前状态：

```text
now -> create -> play -> work -> depart -> chat
```

实现要求：

- 转场期间暂时锁定重复点击，或只保留最后一个目标状态；
- 导航点击必须支持键盘；
- `prefers-reduced-motion` 下使用短淡入/淡出或直接替换；
- 直接访问某个内容 URL 时，不要求用户先完成场景动画；
- 状态和内容 URL 可互相映射，方便分享和搜索。

## 7. 技术实施边界

### 7.1 建议技术栈

仓库目前没有既定前端框架。建议：

- React + Vite + TypeScript；
- Three.js / React Three Fiber；
- GSAP 或同类时间线工具负责场景和物件转场；
- React Router 管理状态和内容 URL；
- Markdown/MDX 或结构化内容文件管理文章、项目、旅行和猫记录；
- 真实内容使用 HTML/CSS，WebGL 只负责场景与物件表现。

### 7.2 场景数据模型

每个场景至少需要描述：

- `stateId`：`now`、`create`、`play`、`work`、`depart`、`chat`；
- `environment`：背景、灯光、地面、环境音；
- `avatarAnchor`：共享的角色位置和旋转；
- `hotspots`：物件、内容集合、移入反馈和点击行为；
- `palette`：当前场景的主色和 active color；
- `transitionProfile`：进场、退场和与其他状态的物件变形规则。

新增内容时优先新增内容记录，不新增 3D 场景：

```text
content item
  -> cluster
  -> scene
  -> object hotspot
  -> content presentation
  -> public URL
```

### 7.3 资产边界

需要独立制作、可复用的资产：

- MouT 体素/2.5D 角色；
- 烧酒和小八的体素或低面数模型；
- 三阶魔方；
- GBA；
- 报纸和内容纸张材质；
- CrossPod 麦克风和波形；
- 独立产品原型发射台及可插拔模块；
- AI Agent 核心和工具模块；
- 车内、车窗、路书和目的地背景层；
- 需要真实展示的个人截图、照片、音频和试玩项目。

生成概念图不能直接作为最终生产素材。最终资产需要独立、可替换、可压缩和可在 Three.js 中控制。

### 7.4 性能与降级

- 只加载当前场景和最可能的下一个场景；
- 使用低面数模型、Draco 压缩、纹理图集和按需加载；
- 监听设备性能，在粒子数量、阴影和后处理上自动降级；
- 为不支持 WebGL 或开启减少动画的用户提供 2D Canvas / DOM 场景；
- 提供一个完整的无 3D 内容索引，确保招聘者、搜索引擎和移动端用户可以直接访问内容；
- 3D 失败不能导致文章、项目、音频和联系方式不可用。

## 8. 内容系统

### 8.1 内容聚类

内容的一级组织由场景和主题入口决定，不按公司或职位完全切开：

- 观察与写作：报纸入口；
- 播客与声音：麦克风入口；
- 独立产品：原型发射台；
- 早期 Web 实验：三阶魔方；
- 游戏经历：GBA、游戏机、收藏入口；
- 行业经历：工作场景的五类行业入口；
- 旅途与场外：车窗、电影票、乒乓球拍和猫。

一个内容可以有多个关联，但不需要在首页重复展示多次。例如 CrossPod 属于“播客与声音”，也可以关联“独立产品”；Super Intern 属于“AI / Agent”，也可以关联“独立实验”。

### 8.2 项目内容模板

网站不默认要求完整项目复盘。每个项目至少可以有：

- 一句话：它是什么；
- 一句话：为什么当时想做；
- 关键体验或截图；
- 当前状态；
- 一个真实的个人观察。

只有用户确实想深入时，才展开更多过程、限制、结果和后来改变的看法。“复盘”不是一级导航，也不应成为访客进入网站后的默认阅读姿态。

### 8.3 写作节奏

为了降低持续输出门槛，内容可以分为：

- 短记录：看到一个现象，留下几句话；
- 观察：对一个产品、趋势、电影或经历形成初步判断；
- 长文：完整展开一个问题；
- 作品记录：记录一个产品、实验或可试玩项目。

内容系统应该允许未完成的想法存在，不要求每次发布都像正式文章。

## 9. 分阶段实施顺序

### Phase 0：资料与内容清理

- 整理现有简历、个人经历、社思现场和项目资料；
- 为每条内容建立主题、场景、入口物件和公开状态；
- 核对项目名称、时间和可公开的截图/链接；
- 选出第一批真实素材：一篇短文、一段 CrossPod 音频、一个独立产品入口、GBA 游戏和一条旅行记录。

### Phase 1：角色与共享舞台

- 确认体素角色的尺寸、坐姿、朝向、衣服标记和材质；
- 制作烧酒、小八和三阶魔方；
- 建立固定摄像机、共享坐标系、导航和返回机制；
- 不接入完整内容，只验证角色和场景切换骨架。

### Phase 2：创作场景纵向切片

先完整做通：

`创作 → 报纸预览 → 文章阅读 → 返回 → 波形播放 → 原型发射台`

验证内容层展开、音频播放、URL、返回和移动端降级。

### Phase 3：工作场景与 AI Agent

- 制作 AI Agent 核心和工具模块；
- 接入 Super Intern、Dimensional Inn 等内容集合；
- 实现空间助手式的点击/指针交互；
- 再接入社交、游戏、品牌和电子政务次级入口；
- 确认 AI 核心不会退化成普通聊天窗口。

### Phase 4：游戏与出发

- 接入 GBA 可试玩项目、游戏记忆和收藏入口；
- 制作固定车内和一个目的地场景；
- 先验证“格鲁吉亚 · 巴统”车窗换景；
- 再扩展新疆和日本城市；
- 保持角色和镜头不变。

### Phase 5：完整内容、分身和公开入口

- 接入文章、播客、独立产品、旅行和猫记录；
- 加入 AI 分身公开对话能力；
- 建立 DOM 内容索引、搜索引擎入口和键盘访问；
- 完成移动端、减少动画和 WebGL 不可用时的体验。

### Phase 6：视觉 QA 与发布

- 使用真实浏览器验证桌面和移动尺寸；
- 检查角色在每个状态的位置、比例和姿态；
- 检查所有热点是否有真实内容；
- 检查转场时是否有跳帧、遮挡、错误焦点或重复点击问题；
- 检查 3D 失败时每个内容 URL 是否仍然可访问；
- 记录概念稿与实现截图的差异，再决定是否继续修正。

## 10. 验收标准

### 体验

- 访客不需要自由探索就能理解如何切换状态；
- 每次只有一个场景处于主要呈现状态；
- 角色在所有状态中保持视觉连续；
- 每个主要物件都对应真实经历或内容；
- 物件打开后的内容可读、可听、可玩或可继续访问；
- AI 分身是角色的一部分，不是强行插入的客服组件。

### 设计

- 场景之间有共同的角色和镜头规则，但环境色、材质和情绪不同；
- 画面有体素和 2.5D 语言，但不变成怀旧网页或玩具店；
- 没有默认 Bento、传统 Hero、项目卡片墙或简历答辩结构；
- 颜色和装饰来自 MouT.me 的真实经历，不是无出处的视觉填充；
- 猫有生活感，但不抢走核心内容。

### 工程

- 文章和项目不依赖 WebGL 才能阅读；
- 当前场景之外的重资源不会一次全部加载；
- 低性能、移动端、减少动画和 WebGL 不可用时有合理降级；
- 状态机、内容数据和资产模块边界清晰；
- 新增项目不需要新增一套场景结构。

## 11. 当前未决事项

以下内容暂不阻塞场景设计，但开发前需要确认：

- `此刻` 场景的具体环境和当前项目；
- 体素角色是否保留眼镜的明显轮廓，还是只保留黑发和服装轮廓；
- AI 分身是否支持语音，还是第一版只做文字；
- 猫的互动是否打开独立照片页，还是只作为轻量彩蛋；
- 旅行目的地的第一批公开照片和地点资料；
- 旧个人网站、婚礼小游戏、CrossPod 等项目的可访问 URL；
- 工作经历中企业名称、客户名称和截图的公开边界；
- 文章和项目详情页是否使用 Markdown/MDX，还是先使用结构化 JSON。

## 12. 决策记录

### 已否定

- 传统“Hero + 下方图文排列”的个人主页；
- 以项目分析、商业化复盘和指标证明为首页主线；
- 要求访客在开放世界中自由走动寻找内容；
- 抽象粒子网络作为整个网站的主要内容界面；
- 所有场景统一使用黄色背景；
- 把每个项目都做成一个独立 3D 物件；
- 用普通文件夹直接代表独立产品；
- 把 TIYA、AI VTuber 等工作经历放入创作场景的麦克风入口；
- 把 AI 围棋、UNO、掼蛋、海龟汤、LOL 陪玩直接放入游戏场景。

### 已确认

- 品牌始终使用 `MouT.me`，不简写成 `MouT`；
- 固定体素化角色，环境切换；
- 角色胸前标记使用“永结童心”；
- 每次只呈现一个状态场景；
- 创作场景使用通用报纸、麦克风、独立产品原型仓、三阶魔方和猫；
- 工作场景以 AI / AI Agent 为主焦点，其他行业作为次级来源；
- 出发场景使用固定车内和单一目的地车窗换景；
- 文章、音频、项目和游戏内容使用 HTML/独立 URL 保障可读性；
- Three.js / React Three Fiber 作为 3D 主体，提供 DOM/2D 降级。
